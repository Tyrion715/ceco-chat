CecoChat
Start How it works Services GitHub

A chat engine that grows by adding machines, not by rewriting.

Real-time messaging for millions of users, built as .NET 8 microservices. Clients hold a WebSocket to a Messaging node; the nodes exchange traffic over a Kafka backplane, so two people on different nodes still chat. History lands in Cassandra, users in YugabyteDB, files in MinIO. Everything is cloud-agnostic.

Start in four steps

You need the .NET 8 SDK, Docker with Compose and a machine with plenty of RAM. The local stack runs Kafka, YugabyteDB, Cassandra, Redis, MinIO and the observability tools.

1 · Make a dev certificate

Services and ingress use TLS. In source/certificates run ./create-certificate.sh then ./trust-certificate.sh.

2 · Create volumes, start infrastructure

Run docker-volume.sh in each component folder under deploy/docker, then ./start-main.sh and ./start-telemetry.sh.

3 · Run the services

Config first, since every service reads dynamic configuration from it. Then IdGen, Messaging, Chats, User and BFF with dotnet run from their folders under source/.

4 · Chat

Start the console client in source/CecoChat.ConsoleClient. Messaging has two launch profiles so two instances can run side by side and simulate users on different nodes.

Or start only what you are working on:

cd deploy/docker
docker compose -f kafka.yml up -d
docker compose -f yugabyte.yml up -d
docker compose -f cecochat-config.yml up -d

cd source && dotnet test CecoChat.sln      # integration tests start their stores with Testcontainers

How it works

Live traffic and everything else take different roads.

Sending goes to the recipient's partition

A client sends a message or reaction over WebSocket with MessagePack. The Messaging node asks ID Gen for a Snowflake ID, then publishes to the Kafka partition that belongs to the recipient. Which node the sender is on does not matter.

Receiving listens only to assigned partitions

Each Messaging node subscribes to a set of partitions, and only clients whose user IDs map to those partitions connect to it. Users and their traffic are spread across nodes by user ID, so adding a node adds capacity.

Everything else goes through the BFF

Register, authenticate, edit a profile, search users by name, invite and accept connections, fetch chat history, upload a file: all HTTP/JSON to the Backend For Frontend, which calls the Chats and User services over gRPC. The Chats service builds chat state and history in Cassandra by consuming the same backplane.

Configuration that changes at runtime

The Config service keeps dynamic settings in YugabyteDB and pushes changes to interested services over the backplane. The deployment design has a configurator read metrics and grow or shrink the Messaging partition count and instance count from them.

Scaling is designed in

BFF, User, Chats and ID Gen sit behind a load balancer and scale by instance count. Messaging scales by partitions. Research notes in docs/ cover the concurrent connection limit, expected traffic, message ID design and reliable messaging versus consistency.

What a user can do
  1. Messaging: send and receive messages, send files (images, text, PDF), react and unreact with emojis, several clients per user
  2. Chats: processing notifications, new-message indication, history at any point in time
  3. Users: register, authenticate, change password, edit profile, store small files
  4. Other users: search by name, connections (invite, accept, cancel, remove), public profiles

Operations: health checks, distributed tracing, logs and metrics via OpenTelemetry to Jaeger, Prometheus, Grafana, ElasticSearch and Kibana. Deploys with Docker Compose or to Minikube from deploy/. GitHub Actions build the solution, enforce code style with dotnet format, run SonarCloud and push images to Docker Hub.
